# Migrating from Cronos v1.7 to v1.8

This document is for node operators (validators, RPC providers, archive nodes).
It is a guide to moving a node from v1.7.x to v1.8, with an emphasis on the
**new configuration options**.

Existing configs keep working unchanged: every new option has a working default.
The substantive new feature is the **app-side mempool**, which is opt-in.

---

## 1. Breaking changes (user-facing)

| Change | Who it affects | When it takes effect |
|---|---|---|
| `SendCroToIbc` restricted to authorized contracts | Contracts using the CRO→IBC hook | Upgrade height |
| Interchain Accounts (ICA) removed | ICA users, ICA precompile callers | Upgrade height |
| `MsgTurnBridge` no longer supported | Anyone submitting that message | Upgrade height |
| Minimum gas cost for calldata-heavy transactions | Dapps sending large calldata | Upgrade height |
| Governance parameter bounds tightened | Governance proposers | Upgrade height |
| Per-transaction gas cap of 16,777,216 | Dapps sending very large gas limits | **Not at the upgrade height** — needs a separate governance change |
| Pending-transaction filters return nothing | RPC consumers | Only if you enable the app-side mempool |
| `mempool.max-txs = -1` is now fatal with `type = "app"` | Your node | Only if you enable the app-side mempool |

## 2. Upgrade procedure

The upgrade plan name is **`v1.8`**. The chain halts at the upgrade height and
you swap the binary.

```bash
# 1. Back up (mandatory). Stop the node first for a consistent copy.
sudo systemctl stop cronosd
cp -a ~/.cronos/config ~/.cronos-config-backup-v1.7
# Snapshot ~/.cronos/data by whatever mechanism you normally use (LVM, ZFS, tar).

# 2. Verify your current state before you change anything.
cronosd version          # expect a v1.7.x value
cronosd status | jq .

# 3a. With cosmovisor: stage the new binary and let it swap at the upgrade height.
mkdir -p ~/.cronos/cosmovisor/upgrades/v1.8/bin
cp /path/to/new/cronosd ~/.cronos/cosmovisor/upgrades/v1.8/bin/cronosd

# 3b. Manual: leave v1.7 running until it halts at the upgrade height,
#     then replace the binary and start again.

# 4. Restart and watch.
sudo systemctl start cronosd
sudo journalctl -fu cronosd
```

The cosmovisor upgrade directory must be named exactly `v1.8` to match the plan
name.

No manual store migration or state export is needed.

**Do not regenerate `config.toml` or `app.toml` from scratch.** A freshly
generated `app.toml` ships `mempool.max-txs = -1`, which disables the
application mempool and is incompatible with `mempool.type = "app"`. Edit your
existing files, adding only the keys you want to change.

## 3. Suggested configuration per role

### Validator

```toml
# config.toml
[mempool]
type = "app"
recheck = true
size = 10000
reap_interval = "500ms"
reap_max_bytes = 1048576
reap_max_gas = 60000000       # mainnet block max_gas; check your own chain
```

```toml
# app.toml
[mempool]
max-txs = 10000
feebump = 10

[cronos]
disable-optimistic-execution = false    # keep optimistic execution on

[rocksdb]
node_type = "validator"

[evm]
block-executor = "block-stm"
block-stm-workers = 0
block-stm-pre-estimate = true

[memiavl]
enable = true
zero-copy = true
```

### Public RPC

```toml
# config.toml
[mempool]
type = "app"
recheck = true
reap_interval = "500ms"
reap_max_bytes = 1048576
reap_max_gas = 60000000       # mainnet block max_gas; check your own chain
```

```toml
# app.toml
[mempool]
max-txs = 10000               # required with type = "app"; see 4.1
feebump = 10

[cronos]
disable-optimistic-execution = false

[rocksdb]
node_type = "rpc"

[evm]
block-executor = "block-stm"
block-stm-workers = 0         # 0 = every CPU; pin below your core count if queries starve
block-stm-pre-estimate = true

[memiavl]
enable = true
zero-copy = true

[json-rpc]
api = "eth,net,web3,debug,cronos,txpool"
```

**Switch to `flood` if you must serve CometBFT's pending-transaction view.**
Under `type = "app"`, CometBFT's own pool is always empty, so
`/unconfirmed_txs` and `/num_unconfirmed_txs` return nothing. Under
`type = "flood"`, those work but `txpool_content` and `txpool_status` return
empty, because they read the app-side pool. Pick whichever your consumers
depend on.

```toml
# config.toml
[mempool]
type = "flood"
```

The `reap_*` keys and the new `[cronos]` mempool options are ignored under
`flood`.

**Keep Block-STM or optimistic execution on.** Do not switch this node to
`block-executor = "sequential"` together with
`disable-optimistic-execution = true`: that is the only combination that turns
on the memiavl node cache, and on this release the cache can halt the node with
an app hash mismatch. See [6.2](#62-do-not-enable-the-memiavl-node-cache).

### Archive

Same reasoning as Public RPC: the app-side mempool by default, and `flood`
only if your consumers need CometBFT's pending-transaction view. On an archive
node that sees little submission traffic, the mempool type makes little
difference to performance.

Complete configuration:

```toml
# config.toml
[mempool]
type = "app"
recheck = true
reap_interval = "500ms"
reap_max_bytes = 1048576
reap_max_gas = 60000000       # mainnet block max_gas; check your own chain
```

```toml
# app.toml
[mempool]
max-txs = 10000               # required with type = "app"; see 4.1
feebump = 10

[cronos]
disable-optimistic-execution = false

[rocksdb]
node_type = "archive"

[evm]
block-executor = "block-stm"
block-stm-workers = 0         # 0 = every CPU; pin below your core count if queries starve
block-stm-pre-estimate = true

[memiavl]
enable = true
zero-copy = true

[versiondb]
enable = true                 # serves historical queries; unchanged from v1.7

[json-rpc]
api = "eth,net,web3,debug,cronos,txpool"
```

To switch to `flood`, set `type = "flood"` in `config.toml` exactly as for
Public RPC.

Keep Block-STM and `zero-copy = true`, as for Public RPC, and do not enable
the memiavl node cache (see
[6.2](#62-do-not-enable-the-memiavl-node-cache)). With versiondb enabled, every
query, including latest-height queries and `eth_call`, is served from
versiondb rather than memiavl, so memiavl's `zero-copy` and `cache-size` have
no effect on query speed here anyway.

## 4. New configuration: app-side mempool

Until v1.8, CometBFT held the pending-transaction pool. In v1.8 you can hand
that job to Cronos itself with `mempool.type = "app"` in `config.toml`.

What you get by enabling it:

- Transactions relayed by peers are validated exactly as thoroughly as ones
  submitted to your own RPC endpoint, instead of being trusted until block
  building.
- Revalidating the pool after each block no longer happens on the consensus
  path, so it stops competing with block production.
- The `txpool_*` RPCs report the real pool.
- Admission and block building do less redundant work per transaction.

### 4.1 Mandatory pairing

`mempool.type = "app"` lives in `config.toml`. The *size* of the pool lives in
`app.toml` under `mempool.max-txs`, and its default is `-1`, meaning "reject all
insertions".

Set one without the other and the node refuses to start:

```
panic: mempool.type=app is incompatible with NoOpMempool
```

So if you set `type = "app"`, you must also set a positive `max-txs`:

```toml
# app.toml
[mempool]
max-txs = 10000
```

`> 0` caps the pool at that many transactions; `0` means unbounded; `-1`
disables it. This value also sizes three internal caches (sender cache,
encode/decode cache, ante cache), so it is the single most important mempool
number to get right.

### 4.2 `config.toml` — `[mempool]`

```toml
[mempool]

# Switch to the app-side mempool. Valid: "flood" (default), "app", "".
type = "app"

# Post-block revalidation of the remaining pool. Keep true.
recheck = true

# Maximum number of transactions CometBFT will track. Default 5000.
size = 10000

# --- the four options below are new in v1.8 and only apply to type="app" ---

# Cache of transaction hashes already seen, so the same tx is not gossiped
# repeatedly. Default 100000.
seen_cache_size = 100000

# Byte ceiling on each batch of transactions pulled out of the pool for gossip.
# 0 = no limit (default).
reap_max_bytes = 1048576

# Gas ceiling on each batch. 0 = no limit (default).
# Set to your chain's block max_gas: 60000000 on Cronos mainnet.
reap_max_gas = 60000000

# How often transactions are pulled out of the pool for gossip.
# MUST be > 0 when type="app" or the node fails to start. Default 500ms.
reap_interval = "500ms"

# How long before a transaction is eligible for revalidation retry.
# Default 5s. New in v1.8.
check_tx_retry_delay = "5s"
```

| Option | Default | Recommended | Why |
|---|---|---|---|
| `type` | `"flood"` | `"app"` | The main new feature. Use `"flood"` only on nodes whose users need pending-transaction filters — see [4.5](#45-pending-transaction-rpcs-change-behaviour). |
| `recheck` | `true` | `true` | Setting it to `false` disables **all** post-block revalidation, including the expiry of stale transactions. A transaction that has become invalid would then never be dropped and could be re-proposed indefinitely. The node logs a warning if you do this. |
| `size` | `5000` | `10000` | Match it to `app.toml` `mempool.max-txs` so both sides agree on capacity. Raise both together under heavy traffic. |
| `seen_cache_size` | `100000` | leave at default | Only a duplicate filter; the default is already generous. Lowering it increases redundant gossip traffic. |
| `reap_max_bytes` | `0` (no limit) | `1048576` | Bounds each gossip batch, which keeps network bursts predictable. |
| `reap_max_gas` | `0` (no limit) | `60000000` on mainnet | Set it to your chain's `max_gas` consensus param — **`60000000` on Cronos mainnet**. Setting it higher is pointless: a gossip batch would then be allowed more gas than a block can hold. Setting it lower makes it, rather than `mempool-txs-per-block`, the cap that actually binds. Confirm your own value with `cronosd query consensus params` before copying the number. |
| `reap_interval` | `"500ms"` | `"500ms"` | Must be positive under `type="app"`. 500ms is about one block, which is what the per-block budgets below assume. |
| `check_tx_retry_delay` | `"5s"` | leave at default | No known reason to tune it. |

### 4.3 `app.toml` — `[mempool]`

```toml
[mempool]

# Pool capacity. -1 = disabled (default!), 0 = unbounded, >0 = capped.
max-txs = 10000

# Minimum percentage fee increase required to replace a pending transaction
# with the same sender and nonce.
feebump = 10
```

`feebump = 10` means a replacement must offer at least 110% of the original's
priority. This is the "gas bump" behaviour EVM users expect. Set it before
enabling the app mempool — leaving it unset makes replacement looser than users
assume.

### 4.4 `app.toml` — `[cronos]`

Five new options. **All have working defaults — you do not need to add any of
them unless you are tuning.**

```toml
[cronos]

# --- carried over from v1.7 ---
disable-tx-replacement = false
disable-optimistic-execution = false

# --- new in v1.8 ---

# Cache for transaction encode/decode results.
# 0 = size it from app.toml mempool.max-txs (recommended). -1 = disable.
mempool-tx-cache-size = 0

# How long before the same transaction may be gossiped to peers again.
# Default "15s".
mempool-gossip-ttl = "15s"

# Transaction budget per block. Caps both the gossip batch and the
# post-block revalidation batch. 0 = unlimited. Default 2900.
mempool-txs-per-block = 2900

# Drop pooled transactions older than 120 blocks. Default true.
mempool-tx-ttl-enabled = true

# Cache the answer to pending-transaction queries. Default true.
mempool-pending-tx-cache-enabled = true
```

**`mempool-tx-cache-size`** — Avoids re-decoding the same transaction on each
step into a block. *Leave at `0`, which sizes it from `mempool.max-txs`; `-1`
turns it off and also slows down block proposal.*

**`mempool-gossip-ttl`** — Stops the node re-broadcasting its whole pool to every
peer several times a second. *Leave at `"15s"`; shortening it costs bandwidth.*

**`mempool-txs-per-block`** — One budget for both how many transactions are
gossiped per batch and how many are revalidated after each block; the default
`2900` is an empirical mainnet figure, and since that implies about 20.7k gas
each against mainnet's 60M `max_gas`, `reap_max_gas` is what binds first on
calldata-heavy batches. *Leave at `2900` unless your real transactions-per-block
differs a lot; if it does, set it near your observed p99.*

**`mempool-tx-ttl-enabled`** — EVM transactions never expire on their own, so
without this a transaction the proposer keeps skipping would sit in the pool
forever; this drops anything older than 120 blocks. *Leave `true` — it is the
pool's only cleanup for stuck transactions.*

**`mempool-pending-tx-cache-enabled`** — Caches the pending-transaction query
result, which otherwise scans the whole pool. *Leave `true`, especially on RPC
nodes.*

### 4.5 Pending-transaction RPCs change behaviour

When Cronos owns the pool, CometBFT's own pool is empty. So under
`type = "app"`:

- CometBFT's `/unconfirmed_txs` and `/num_unconfirmed_txs` return nothing.
- `eth_newPendingTransactionFilter` and the `pending` filter return nothing.
- `txpool_content` and `txpool_status` work.

If you run a public endpoint whose users depend on pending-transaction filters,
either keep `type = "flood"` on those nodes or move consumers to `txpool_*`,
which needs the namespace enabled:

```toml
# app.toml
[json-rpc]
api = "eth,net,web3,debug,cronos,txpool"
```

### 4.6 Per-transaction size ceiling

The size ceiling for cached transactions is not a `[cronos]` option. It comes
from `config.toml`:

```toml
[mempool]
max_tx_bytes = 1048576   # 1MB, default
```

Transactions larger than this are not cached but are still processed normally.
Nothing validates this value against any `[cronos]` option and nothing fails at
startup because of it. *Recommendation: leave at the 1MB default.*

## 5. New configuration: `[rocksdb] node_type`

New in v1.8. Picks a storage tuning profile based on what the node is for.
**Experimental**, and only has an effect on RocksDB backends.

```toml
# app.toml
[rocksdb]
node_type = ""
```

| Value | Tuned for |
|---|---|
| `""` (default) | Standard configuration, safe everywhere. |
| `"validator"` | Lowest-latency state reads during block execution. |
| `"rpc"` | Highly concurrent reads — `eth_call`, state queries. |
| `"archive"` | Large historical scans — `eth_getLogs`. |

Any other value fails at startup with an error listing the allowed values.

*Recommendation: set it to match the node's role. Because it is experimental,
roll it out to one node first and compare block-execution and query latency
against an unchanged peer before applying it fleet-wide. Leaving it `""` is a
perfectly safe choice.*

## 6. Block-STM and memiavl

These existed in v1.7. On this release the same settings are recommended for
every role.

Validator baseline — optimise for block execution:

```toml
# app.toml
[evm]
# "block-stm" for parallel execution; "sequential" is the default.
block-executor = "block-stm"
block-stm-workers = 0          # 0 = use all available CPUs
block-stm-pre-estimate = true

[memiavl]
enable = true
zero-copy = true
```

### 6.1 Recommendation by role

**All roles: Block-STM on, `zero-copy = true`, optimistic execution on.**
Use the baseline above on validators, RPC and archive nodes alike.

- **Validators** need low block-execution latency.
- **RPC and archive nodes** still execute every block, and a node that falls
  behind serves stale state to every query. If Block-STM competes with query
  serving for CPU, pin `block-stm-workers` below your core count rather than
  turning Block-STM off.

**Keep `zero-copy = true`.** Setting `zero-copy = false` has one benefit:
it re-enables the SDK address cache. Block-STM also switches that cache off,
so with Block-STM on, `zero-copy = false` adds a copy to every latest-height
read and gains nothing. It also does **not** make historical queries safer:
reads at a past version already copy unconditionally.

### 6.2 Do not enable the memiavl node cache

`memiavl.cache-size` (default `1000`) only takes effect when **both**
`block-executor = "sequential"` and `disable-optimistic-execution = true` are
set; otherwise the node forces it to `0`. On this release, do not run that
combination with a non-zero `cache-size`.

**Why:** the cache is not safe against reads that run concurrently with block
commit. During `FinalizeBlock`, the node writes the block's changes into the
live memiavl tree. Two kinds of reader can read that tree at the same moment
without a lock:

- CheckTx, under `mempool.type = "app"`, where it no longer takes the ABCI lock.
- gRPC and JSON-RPC queries at the latest height, on nodes without versiondb.

If such a read of a key overlaps the block's write to the same key, the cache
can keep the old value. The next block then reads that stale value, computes a
different app hash from the rest of the network, and the node halts. Sender
accounts and balances are read in CheckTx and written in almost every block,
so on a busy node the overlap is likely rather than theoretical.

**What to do:**

- Keep the recommended configuration (Block-STM or optimistic execution on).
  The cache is then forced off and the node is not affected.
- If you must run `sequential` with optimistic execution disabled, set the
  cache off explicitly:

  ```toml
  # app.toml
  [memiavl]
  cache-size = 0
  ```

This will be lifted once the node ships the upstream memiavl fixes for
concurrent reads.
