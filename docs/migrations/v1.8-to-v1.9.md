# Migrating from Cronos v1.8 to v1.9

---

## 1. Breaking changes (user-facing)

| Change | Who it affects | When it takes effect |
|---|---|---|
| Block-STM keys under `[evm]` are no longer read | Every node that enabled Block-STM on v1.8 | When the node starts on the v1.9 binary |
| RPC admission is capped at 8192 txs in flight by default ([3.2](#32-rpc-transaction-admission-is-capped)) | `mempool.type = "app"` nodes whose RPC clients send more than 8192 txs at once | When the node starts on the v1.9 binary |
| Rotating a consensus key costs 1 bond-denom unit ([4.1](#41-consensus-key-rotation-fee)) | Validators that rotate their consensus key | At the upgrade height |
| Staking `HistoricalInfo` may be deleted ([4.2](#42-staking-historical-info)) | Clients that query `cronosd query staking historical-info` or `/cosmos/staking/v1beta1/historical_info/*` | At the upgrade height |
| `cronosd tx cronos migrate` is removed | Operators that migrate genesis files with it | When the node starts on the v1.9 binary |

For changes that come from Cosmos SDK v0.55 itself (`x/params` and
`SIGN_MODE_TEXTUAL` removed, new auth and feegrant migrations), see the SDK's
[UPGRADING.md](https://github.com/cosmos/cosmos-sdk/blob/release/v0.55.x/UPGRADING.md).

## 2. Upgrade procedure

The upgrade plan name is `v1.9`.

> **To be completed** once the v1.9 upgrade height is fixed.

### 2.1 Before you upgrade

Do these checks **before** the node starts on the v1.9 binary.

**Block-STM settings.** Show every Block-STM line in your `app.toml`. The
top-level copy is printed first, the `[evm]` copy second:

```bash
grep -nE '^(block-executor|block-stm-workers|block-stm-pre-estimate)' ~/.cronos/config/app.toml
```

If only the `[evm]` copy is set to `"block-stm"`, copy the three values to the
top-level keys now. An `app.toml` generated by v1.8 already contains the
top-level keys, set to `block-executor = "sequential"`, so a node that only
edited `[evm]` switches to sequential execution on v1.9. See
[3.1](#31-block-stm-settings-moved-out-of-evm).

Top-level keys must appear above the first `[section]` header in the file;
TOML assigns any key below a header to that section.

**Block size.** v1.9 reserves about 3.4 KB per validator in every block for
the commit, sized for ML-DSA-65 signatures whatever key type each validator
uses. Check that `block.max_bytes` (`cronosd q consensus params`) leaves room
for transactions after the commit at `max_validators` (`cronosd q staking
params`) and up to `evidence.max_bytes` of evidence, or block building panics.

### 2.2 After you upgrade

**Block-STM settings.** Delete the `[evm]` copy. v1.9 no longer reads it, and
a freshly generated v1.9 `app.toml` no longer contains it:

```toml
# app.toml
block-executor = "block-stm"
block-stm-workers = 0          # 0 = use all available CPUs
block-stm-pre-estimate = true

[evm]
tracer = ""
```

Confirm which executor the node installed. It logs one of these lines at
startup:

```text
installing block-stm tx runner  module=baseapp pre_estimate=true workers=<n> wrapped=true
installing sequential tx runner module=baseapp wrapped=true
```

```bash
sudo journalctl -u cronosd | grep -E 'installing (block-stm|sequential) tx runner' | tail -1
```

## 3. Configuration changes

### 3.1 Block-STM settings moved out of `[evm]`

v1.8 carries the three Block-STM keys twice in `app.toml`: at the top level,
and under `[evm]`. v1.8 reads only the `[evm]` copy. v1.9 reads only the
top-level copy.

| Key | v1.8 reads | v1.9 reads |
|---|---|---|
| Executor | `[evm] block-executor` | top-level `block-executor` |
| Worker count | `[evm] block-stm-workers` | top-level `block-stm-workers` |
| Pre-estimation | `[evm] block-stm-pre-estimate` | top-level `block-stm-pre-estimate` |

The values and their meaning are unchanged: `block-executor` is `"block-stm"`
or `"sequential"` (the default), `block-stm-workers = 0` uses every available
CPU, and `block-stm-pre-estimate` enables write-set pre-estimation.

v1.9 ignores a leftover `[evm]` copy without an error or warning. If the two
copies disagree, v1.9 follows the top-level keys.

The three keys can now also be set when starting the node. On v1.8 none of
them was accepted as a flag:

```bash
cronosd start --block-executor block-stm --block-stm-workers 0 --block-stm-pre-estimate
```

A flag overrides the matching `app.toml` key.

### 3.2 RPC transaction admission is capped

New key `[cronos] mempool-rpc-max-inflight`, default `8192`. With
`mempool.type = "app"`, at most this many RPC transactions are admitted at
once. This counts CometBFT's `broadcast_tx_*` and `check_tx`, and the
JSON-RPC methods that submit a transaction (`eth_sendRawTransaction`,
`eth_sendTransaction`, `eth_resend`, `personal_sendTransaction`). Extra ones are
rejected instead of queuing. Peer gossip is not counted. Set `0` to disable
the cap.

How a rejected transaction is reported depends on the endpoint:

- `broadcast_tx_sync` and `check_tx` return code `32000` with log
  `too many in-flight RPC txs`.
- `broadcast_tx_commit` returns the same code and log in its `check_tx`
  field.
- The JSON-RPC methods return an error whose message starts with
  `too many in-flight RPC txs`.
- `broadcast_tx_async` returns success before the check runs, so a rejected
  transaction is dropped without any signal.

Resend a rejected transaction, in nonce order for the same sender. Through
`broadcast_tx_*`, wait at least `[mempool] check_tx_retry_delay` / 10 (0.5s by
default) first: until then CometBFT answers the same bytes with
`tx already seen`. Clients that send bursts should not use `broadcast_tx_async`.

A transaction holds its slot until it is admitted or rejected, including while
it waits for a block commit, so a burst at commit time is the most likely to
hit the cap. Leave the default unless an RPC client legitimately sends more
than 8192 transactions concurrently. The cap is per node, not per client, so
public RPC nodes still need their own rate limiting.

## 4. Cronos settings for Cosmos SDK v0.55 features

### 4.1 Consensus key rotation fee

The upgrade sets the staking `key_rotation_fee` to `1` unit of the bond denom,
instead of the SDK default of `1000000`. The validator operator account pays
it on each `MsgRotateConsPubKey`, and the fee is burned.

The fee comes from the operator account's liquid balance, not its bonded
stake. An operator whose stake is all bonded must get 1 unit before rotating:
a bank transfer from any holder, or an unbond of 1 unit from its
self-delegation, which becomes spendable after `unbonding_time`. The rotation
transaction also pays gas in the EVM denom.

Most operators hold none. As of November 2026, 25 of 29 bonded mainnet
operators and every bonded testnet operator had no liquid stake, and almost
all liquid stake sat in a few genesis-era accounts. Ask the Cronos team for
the 1 unit instead of waiting out an unbond.

The upgrade does not change `validator.pub_key_types`, so validators can only
rotate to the key types it already lists (check `cronosd q consensus params`).
Allowing ML-DSA-65 keys takes a governance proposal that adds `ml_dsa_65`.

Once any validator holds an ML-DSA-65 key, every Cronos header carries it, so
allow the key type only after IBC counterparties and relayers support it:

- Counterparty chains need CometBFT v0.38.26 or later on the v0.38 line, or
  v0.40. Older versions and the v0.39 line (checked at v0.39.4) reject the
  header, and their Cronos light client stops updating.
- Hermes needs the crypto-org-chain/hermes fork at commit `cd4664d8` or later on
  `master`, which builds on a tendermint-rs v0.40 backport of ML-DSA-65 support.
  Upstream releases (checked at v1.13.3) cannot decode the keys.
- `rly` needs the crypto-org-chain/relayer fork built on CometBFT v0.38.26.

### 4.2 Staking historical info

Cronos serves `BLOCKHASH` from the EIP-2935 history contract, so staking
`HistoricalInfo` is no longer needed for it. The upgrade sets staking
`historical_entries` to `0` and deletes the stored `HistoricalInfo` entries,
but only if both hold:

- the EVM `history_serve_window` is greater than `header_hash_num`, and
- the contract itself holds a hash for each of the last `header_hash_num`
  blocks. Hashes only in the older EVM header-hash store do not count.

Otherwise it keeps `historical_entries` unchanged and logs
`keeping staking historical_entries` with the reason. Set it to `0` with a
later gov proposal once the contract has filled that window.

After the deletion, `historical-info` queries return not found from the
upgrade height on. A query pinned with `--height` to an earlier block still
returns the old entries if the node keeps that block's state.
