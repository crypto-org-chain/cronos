# Migrating from Cronos v1.8 to v1.9

---

## 1. Breaking changes (user-facing)

| Change | Who it affects | When it takes effect |
|---|---|---|
| Block-STM keys under `[evm]` are no longer read | Every node that enabled Block-STM on v1.8 | When the node starts on the v1.9 binary |

## 2. Upgrade procedure

> **To be completed** once the v1.9 upgrade plan name and height are fixed.

### 2.1 Before you upgrade

Do these checks **before** the node starts on the v1.9 binary.

**Block-STM settings.** Show every Block-STM line in your `app.toml`. The
top-level copy is printed first, the `[evm]` copy second:

```bash
grep -nE '^(block-executor|block-stm-workers|block-stm-pre-estimate)' ~/.cronos/config/app.toml
```

If only the `[evm]` copy is set to `"block-stm"`, copy the three values to the
top-level keys now. An `app.toml` generated by v1.8 already contains the
top-level keys, set to `block-executor = "sequential"`, so a node that only
edited `[evm]` switches to sequential execution on v1.9. See
[3.1](#31-block-stm-settings-moved-out-of-evm).

Top-level keys must appear above the first `[section]` header in the file;
TOML assigns any key below a header to that section.

### 2.2 After you upgrade

**Block-STM settings.** Delete the `[evm]` copy. v1.9 no longer reads it, and
a freshly generated v1.9 `app.toml` no longer contains it:

```toml
# app.toml
block-executor = "block-stm"
block-stm-workers = 0          # 0 = use all available CPUs
block-stm-pre-estimate = true

[evm]
tracer = ""
```

Confirm which executor the node installed. It logs one of these lines at
startup:

```text
installing block-stm tx runner  module=baseapp pre_estimate=true workers=<n> wrapped=true
installing sequential tx runner module=baseapp wrapped=true
```

```bash
sudo journalctl -u cronosd | grep -E 'installing (block-stm|sequential) tx runner' | tail -1
```

## 3. Configuration changes

### 3.1 Block-STM settings moved out of `[evm]`

v1.8 carries the three Block-STM keys twice in `app.toml`: at the top level,
and under `[evm]`. v1.8 reads only the `[evm]` copy. v1.9 reads only the
top-level copy.

| Key | v1.8 reads | v1.9 reads |
|---|---|---|
| Executor | `[evm] block-executor` | top-level `block-executor` |
| Worker count | `[evm] block-stm-workers` | top-level `block-stm-workers` |
| Pre-estimation | `[evm] block-stm-pre-estimate` | top-level `block-stm-pre-estimate` |

The values and their meaning are unchanged: `block-executor` is `"block-stm"`
or `"sequential"` (the default), `block-stm-workers = 0` uses every available
CPU, and `block-stm-pre-estimate` enables write-set pre-estimation.

v1.9 ignores a leftover `[evm]` copy without an error or warning. If the two
copies disagree, v1.9 follows the top-level keys.

The three keys can now also be set when starting the node. On v1.8 none of
them was accepted as a flag:

```bash
cronosd start --block-executor block-stm --block-stm-workers 0 --block-stm-pre-estimate
```

A flag overrides the matching `app.toml` key.

## 4. Other changes

**The transaction decode cache now also serves sequential execution.** On v1.8
the cache enabled by `mempool.max-txs` (or `[cronos] mempool-tx-cache-size`) was used
during block execution only under Block-STM. On v1.9 it is used under both
executors. No configuration change is needed, and the cache size is unchanged.
